# Venue：发布说明与更新公告

**识别**：版本号 + 更新条目列表 + 面向用户的功能说明；长度从三行到长文不等。

## 本 venue 的典型 slop

（sepia evals 的测试文本就是本 venue 的极端样本：「We're thrilled to announce…this isn't just an update, it's a fundamental reimagining…」）

- 「激动人心地宣布」「全新升级」「重新定义」「不仅仅是 X，更是 Y」
- 每个功能都配「您的反馈是我们的北极星」式用户背书
- 「极致体验」「无缝衔接」「为团队赋能」等不可验证的价值宣言
- 升华收尾（「见证我们的成长」「我们期待与你一起构建未来」）套模板
- 把 bug 修复包装成重大特性

## 编辑策略

- 条目化：每条 = 功能/修复 + 用户可感知的变化（怎么用、什么变了）；无条目信息时用一段话直接说
- 数字保留且写清基准（「导出快 40%」→ 保留，但注明「在内部基准测试中」——无来源的数字删除或标注）
- 删价值宣言与升华收尾；保留一句真实的方向性说明可以
- bug 修复如实写（「修复了 CSV 导入在字段含引号逗号时丢行的问题」——具体、可验证，这就是好的）
- Breaking changes 置顶且不软化

## 必须保留

- 版本号、日期、 breaking changes、迁移说明
- 功能名、参数、入口（菜单路径/命令）
- 感谢的贡献者名单（真实的）
- 安全修复的说明（不淡化严重性）

## 白名单（本 venue 不算 slop）

- 条目列表是格式惯例
- 「新功能」「修复」分类标签是惯例
- 一句真诚的感谢用户/团队不是 slop（模板三连才是）
