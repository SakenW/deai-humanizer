# Venue：PR 回复与 code review 评论

**识别**：GitHub/GitLab 的 PR 描述、review 评论、issue 回复；面向协作者，短平快，技术指涉精确。

## 本 venue 的典型 slop

- PR 描述写成产品发布文（「本 PR 带来了激动人心的改进」）
- review 评论绕弯子（「也许可以考虑一下是否有可能存在……的情况」）——review 要直接
- 「LGTM！只是几个小小的建议」后跟 20 条必改项——语气与内容不符
- 复述 diff 已经显示的内容（「此更改将 X 函数中的 Y 变量重命名为 Z」×10）
- issue 回复复述 issue 原文，最后加「感谢您的反馈，我们会认真考虑」

## 编辑策略

- PR 描述三段式：为什么改（动机/issue 链接）、改了什么（要点列表）、怎么验证（测试/复现步骤）——其余删
- review 评论直给：问题位置 + 建议方案 + 理由一句；级别明确（必改/建议/nit）
- 删除对 diff 的复述；reviewer 看得到 diff
- issue 回复直接答问题或给状态（已修复于 vX.X / 需要更多信息：具体要什么），删客套模板

## 必须保留

- issue/PR 编号引用、commit hash、文件路径与行号
- breaking change 声明与迁移说明（一个字不软化）
- 测试与验证步骤
- 致谢与协作礼貌（真实的一句，不是模板三句）

## 白名单（本 venue 不算 slop）

- 短句、片段句、列表化是惯例（完整句式反而不自然）
- emoji 标记（🚨 ✅ nit:）是团队惯例，保留
- 「LGTM」单发不是 slop——配合大量未解决评论的「LGTM」才是问题
