# Venue：技术文档

**识别**：API 说明、参数表、操作步骤、版本说明、教程；术语密集、代码/命令/路径穿插。

## 本 venue 的典型 slop

- 概念铺垫长于操作内容（「在开始之前，让我们先理解一下什么是……」）
- 每个步骤都配「这样做的目的是」解释腔
- 「强大」「优雅」「无缝」「极致」等营销形容词进入接口描述
- 示例代码后接一段复述代码行为的散文（代码已自明）
- 注意事项写成免责堆叠（「请注意，在使用本功能时，建议您……」）
- 版本/兼容性说明含糊（「大部分情况下」「通常来说」）——技术文档要精确

## 编辑策略

- 直接进入操作：步骤化，命令/参数/路径保持原样（SKILL.md 交付模式已含）
- 删除复述代码的散文；保留代码注释里没有而散文里有的关键前提（环境、权限、前置条件）
- 营销形容词删除或替换为可验证的具体差异（「快 40%」比「性能大幅提升」好——但数字必须有来源）
- 免责堆叠收敛为一句明确的注意事项（适用范围、前置条件、已知限制）
- 版本与兼容性写精确：版本号、行为差异点、迁移动作

## 必须保留

- 参数全名与类型、命令原样、路径、URL、版本号、YAML/代码块
- 前置条件与权限要求
- 已知限制与破坏性变更警告（一个字都不能软化）

## 白名单（本 venue 不算 slop）

- 步骤编号与命令块是格式惯例
- 重复出现的「注意：」标记是文档惯例（只要内容有实质）
- 正式的完整句式是语域要求，不是 AI 证据
